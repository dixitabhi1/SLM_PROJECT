0. Correction Note (from prior draft)

Two constraints, not one, and they apply to different parts of the system:
    • The proposed architecture contains zero LLMs. The decomposer, router, every
      model in the capability pool, and the aggregator are all SLMs, capped at roughly ≤8B
      parameters. Nothing in the system that ships or gets deployed calls a large model.
    • The comparison baseline is a large LLM (a single frontier-class or large open-weight
      model, e.g. 70B+), answering the query directly with no decomposition.
So the actual research claim is sharper than “many small models vs. one small model”: it’s
“can an entirely SLM-based, decomposed system match or beat a single large LLM
on latency, cost, and quality?” This is a harder claim than the SLM-vs-SLM version — a
single strong LLM is a genuinely tough bar on quality — but it’s also the more valuable result if
it holds, since it directly supports the practical pitch (self-hostable, cheap, no LLM dependency)
against the thing people actually compare it to in practice.



1. Problem Statement

Modern AI search systems typically route every query to one large, general-purpose LLM. This
is simple and usually high-quality, but expensive and slow, especially for compound, multi-
domain queries that don’t need the full weight of a frontier model applied to every sub-part.
The open question: can a fully SLM-based system — decomposing the query and routing sub-
parts to specialized small models running in parallel — match a large LLM’s quality while cutting
latency and cost, or does it fall short on quality in ways that make the savings not worth it?

RQ3 is the one to take most seriously — it’s entirely plausible that a well-orchestrated SLM
network still loses to a strong LLM on harder reasoning subtasks. That result would still be a
valid, useful finding (it would tell you exactly where specialization can and can’t substitute for
scale); it just needs to be reported honestly rather than reframed as a win.

3. Goals

    • Produce a benchmarked, paired comparison (latency, cost, quality) between the all-SLM
      pipeline and a single large-LLM baseline, with confidence intervals, not point estimates.
    • Produce a labeled dataset of decomposable queries with gold-standard task graphs.
    • Identify the complexity threshold where the SLM pipeline’s advantage (or disadvantage)
      crosses over.
    • Demonstrate the proposed system runs with zero LLM dependency — self-hostable on
      SLM-scale compute — while quantifying exactly what quality trade-off (if any) that entails
      against an LLM.

4. Non-Goals

    • Not building a production-grade, user-facing search product.
    • Not training new foundation models — only prompting/fine-tuning existing open-weight
      SLMs (≤8B) for the architecture; the LLM baseline is used as-is, not modified.
    • Not claiming architectural novelty for the decompose-route-parallelize-aggregate pattern
      itself — the contribution is the empirical result for an all-SLM system benchmarked directly
      against an LLM.

6. Stakeholders / Audience

Primarily: yourself as researcher, a potential academic advisor/reviewer, and a technical audi-
ence assessing the claims for correctness. Every artifact should survive an adversarial techni-
cal read, not just a demo.

7. Scope

In scope: eval dataset construction, LLM baseline, 3–5 SLM pool (all ≤8B, zero LLMs in the
proposed system), decomposition + routing + orchestration + aggregation pipeline, controlled
experiments, statistical analysis, written report.
Out of scope (this phase): production hosting/scaling, user-facing UI, fine-tuned decom-
poser/router (candidates for a follow-up phase), any LLM component inside the proposed ar-
chitecture itself.
